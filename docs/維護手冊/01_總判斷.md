# 01　總判斷：你需要學到什麼程度

> 這一章回答「我到底要學多少」。結論先講，理由在後面。
> 所有判斷都根據 2026-09-24 實際讀過的 repository（commit `1892eae`），不是一般論。

---

## 一句話結論

**你不需要成為工程師，也不需要看懂全部程式碼。**
你需要的是「**讀得懂地圖、改得動小地方、驗得出對錯、退得回上一版**」這四種能力。
以這個專案的規模與結構，這是零基礎的人花 **約 20～40 小時有方向的練習** 可以達到的程度。

但是也要講清楚：**有一類問題你大概修不了，也不該硬修**（GPU／CUDA 函式庫、手機編譯 whisper.cpp）。
對這類問題，正確的策略不是「學會修」，而是「**退回已知可用的版本**」。這份手冊會教你怎麼退。

## 第一個要修正的觀念：你的工具「不是」三套程式

你原本的理解是「三個版本各自有自己的程式碼、執行方式、環境與不同的架構」。
**實際讀完程式碼後，這個理解只對了一半。**

| 部分 | 三台共用？ | 說明 |
|---|---|---|
| `ytscript.py`（核心程式，1,930 行） | **三台共用同一個檔案** | 同一份檔案在執行時自己判斷「我在哪種機器上」 |
| `ui.html`（畫面） | **三台共用同一個檔案** | 手機只是在窄螢幕時換排版 |
| `tokens.css`（樣式） | **三台共用** | |
| `安裝.bat`、`start.vbs` 等 | 只有桌機與筆電用 | 桌機和筆電用的是**完全相同**的檔案 |
| `android/install.sh` | 只有手機用 | |

也就是說：

- **GPU 桌機版和無獨顯筆電版，檔案一模一樣。** 差別只在：
  1. 安裝時，`安裝.bat` 偵測到沒有 NVIDIA 顯卡就不裝 CUDA 函式庫
  2. 執行時，`ytscript.py` 裡的 `pick_device()` 偵測不到 GPU 就改用 CPU
- **手機版也是同一份 `ytscript.py`。** 差別只在：
  1. 安裝方式不同（`android/install.sh`）
  2. 執行時偵測到 Termux（`IS_TERMUX`），AI 聽寫改走 whisper.cpp 而不是 faster-whisper

**這對你是非常好的消息。** 它代表：

- 你改一次提示詞、改一次畫面，**三台都會一起變**，不用改三次
- 你需要理解的核心只有 **一個 Python 檔 + 一個 HTML 檔**
- 「三個版本不同步」這個你擔心的問題，本質上只是「三台機器有沒有都更新到 GitHub 上的最新版」

真正「三台不同」的地方只有四小塊，第 02 章有完整對照：
1. 安裝腳本（`安裝.bat` vs `android/install.sh`）
2. 啟動方式（`start.vbs` vs `~/ytscript/start.sh`）
3. AI 聽寫引擎（`engine_whisper` vs `engine_whispercpp`）
4. GPU 判斷（只有桌機會走到）

## 你的想法：哪些正確、哪些需要修正

### 正確的地方

1. **「以實際專案反推要學什麼」是對的。** 一般 Python 教科書 80% 的內容這個專案用不到。
2. **「讓 AI 寫、自己驗證」是合理的長期策略。** 前提是你有「驗證」與「退回」的能力（見下）。
3. **擔心「AI 寫的程式我不懂」是對的擔心。** 但解法不是讀懂每一行，而是知道每一塊在做什麼、改了之後要測什麼。
4. **重視 Git 是對的。** 對你來說，Git 不是工程工具，是**保險**。有了它，AI 改壞什麼都救得回來。

### 需要修正的地方

1. **「三個版本各自獨立」→ 實際是「一份核心、三種安裝方式」。**（見上）
2. **「怕 AI 消失」→ 真正的長期風險其實不是 AI，而是外部依賴。**
   這個工具最常壞掉的原因，排名大概是：
   1. YouTube 改版，`yt-dlp` 或 `youtube-transcript-api` 需要更新（**最常見**，而且修法就是更新套件，不用改程式）
   2. 套件自動升級到不相容的版本（因為目前所有安裝腳本都是「永遠裝最新版」）
   3. Windows／NVIDIA 驅動／Termux 系統更新
   4. 你（或 AI）改程式改壞了

   前三種跟你會不會寫程式關係不大，關鍵是「**知道現在裝的是什麼版本、知道怎麼退回去**」。
3. **「要能修所有 bug」→ 不需要。** 有些 bug 的正確處理是「退回上一版 + 等上游修好」。
   能分辨「這個我該修」和「這個我該退」本身就是維護能力。
4. **「新增功能 → 更新其他版本 → 再測試」→ 你不需要「更新其他版本」這個步驟去改程式**，只需要在另外兩台 `git pull`。

## 回答你的十個問題

### 1. 我的想法哪些地方正確？
見上方「正確的地方」。

### 2. 哪些地方需要修正？
見上方「需要修正的地方」。最重要的是第 1 點（不是三套程式）與第 2 點（真正的風險是外部依賴）。

### 3. 我是否真的需要理解全部程式碼？
**不需要。** `ytscript.py` 1,930 行裡，大約：

| 區塊 | 行數比例 | 你需要的程度 |
|---|---|---|
| 提示詞、輸出格式（`PROMPT_*`、`build_markdown`） | 約 15% | **要能讀懂、能自己改** |
| 主流程（`transcribe`、`assemble`） | 約 10% | **要能讀懂流程順序** |
| 網頁伺服器（`Handler`、`serve`） | 約 10% | 知道它在做什麼、在哪裡 |
| 三個引擎（字幕 API、yt-dlp、Whisper） | 約 35% | 知道誰先誰後、失敗會怎樣 |
| GPU／CUDA／記憶體偵測 | 約 10% | **只要知道位置**，出事時退版本 |
| 字幕格式解析、正規表示式 | 約 10% | 交給 AI，用自我檢查驗證 |
| 快取、工具函式 | 約 10% | 知道用途 |

### 4. 我應該理解到哪個深度？
**「能讀、不必會寫」的深度。** 具體標準是：

- 看到一個函式（`def xxx(...)`），能說出「它收什麼、做什麼、回傳什麼、誰呼叫它」
- 看到 AI 給的修改（diff），能說出「它改了哪幾個地方、有沒有動到我沒要求的地方」
- 看到錯誤訊息，能找到「是哪個檔案、哪一行、哪個函式」

不需要：自己從零寫出一個函式、理解 CUDA 怎麼運作、會寫正規表示式。

### 5. 哪些程式碼可以交給 AI？
- 寫新的函式、改既有函式的內部邏輯
- 正規表示式（`re.compile(...)` 那些看起來像亂碼的東西）
- 字幕格式解析（`_parse_json3` 等）
- HTML／CSS 排版調整
- 解釋錯誤訊息
- 解釋某一段程式在做什麼

### 6. 哪些東西我不能完全交給 AI？
這幾件事 **AI 做不到或做了你也不能信**，必須你自己來：

1. **決定要改什麼**、以及「改到哪裡為止」（AI 很喜歡順手重構）
2. **實際執行測試並看結果**（AI 看不到你的電腦；它說「應該可以」不算數）
3. **在改之前先開 branch 或 commit**（這是你的保險，AI 不會替你記得）
4. **檢查 diff**：AI 給的修改有沒有刪掉不該刪的東西
5. **記錄「已知可用的版本」**（哪個 commit、哪組套件版本是好的）
6. **判斷要修還是要退**
7. **手機上的操作**（AI 沒辦法替你按手機）

### 7. 我需要學哪些 Python？
只學「**讀**這個專案會遇到的」。完整清單在第 04 章，每個都附上它在你專案裡出現的位置：

`import`、變數與 `=`、字串 `"..."` 與 `"""..."""`、`def` 函式與 `return`、呼叫函式、
字典 `{"key": value}` 與 `d.get("key")`、串列 `[...]`、`if / elif / else`、`for`、
`try / except / finally`、`raise`、縮排的意義、`#` 註解、`True / False / None`。

**不用學：** `class` 的設計（只要知道 `Handler` 是一個 class）、`threading` 的原理、
`ctypes`、`lambda` 的細節、`global`、裝飾器、`async`（這個專案的 Python 端沒有用到）。

### 8. 我需要學哪些 Git／GitHub？
第 05 章從零教。必學的只有十幾個指令：

`clone`、`status`、`diff`、`add`、`commit`、`push`、`pull`、`log`、
`switch -c`（開分支）、`switch`（切分支）、`merge`、`restore`（丟掉修改）、`revert`（撤銷某次 commit）、`tag`（標記好版本）。

**不用學：** `rebase`、`cherry-pick`、`submodule`、`reset --hard`（危險，除非照手冊步驟）、GitHub Actions、Pull Request 流程（一個人維護用不到）。

### 9. 我需要學哪些其他技術？
| 技術 | 程度 | 為什麼 |
|---|---|---|
| **終端機（命令提示字元／Termux）** | 必須會用 | 所有操作都從這裡下指令 |
| **pip（Python 套件管理）** | 必須會用 | 更新套件、退回套件版本 |
| HTML | 能認得 `id="..."`、`<button>` | 改畫面時要找到位置 |
| JavaScript | 能認得 `addEventListener`、`fetch` | 知道按鈕按下去呼叫誰 |
| CSS | 知道 `tokens.css` 管顏色間距 | 改外觀時交給 AI |
| JSON | 能讀懂 `{"key": "value"}` | 前後端傳資料的格式 |
| Termux／Linux 基本指令 | `cd`、`ls`、`cp`、`cat` | 手機維護 |
| CUDA／GPU | 只要知道「它是讓 AI 聽寫變快的加速器」 | 出事就退版本 |
| whisper.cpp 編譯 | 只要知道「install.sh 會自動做」 | 出事就重跑 install.sh |
| iOS | **完全不用** | 專案不支援 iOS |
| 資料庫 | **完全不用** | 專案沒有資料庫（快取只是 JSON 檔） |
| 雲端、帳號、API key | **完全不用** | 專案全部在本機執行 |

### 10. 以這個專案來說，我最終應該具備什麼程度，才算真正具有「自主維護能力」？

**用能力來定義，不用「懂多少」來定義。** 下面十項你都能自己做到，就是具備自主維護能力：

| # | 能力 | 驗證方式（自己做一次） |
|---|---|---|
| 1 | 說得出使用者按「開始轉錄」後，資料經過哪些函式 | 不看手冊，畫出第 04 章的流程圖 |
| 2 | 任何需求，找得到要改哪個檔案的哪個地方 | 用第 02 章對照表，找出 5 個需求的位置 |
| 3 | 改之前先開 branch | 第 05 章練習 3 |
| 4 | 用固定提示詞請 AI 修改，並拿到「只改該改的地方」的結果 | 第 08 章提示詞走一次 |
| 5 | 看得懂 diff，判斷 AI 有沒有亂改 | 第 08 章的檢查清單 |
| 6 | 跑自我檢查並看懂結果 | `python tools/selfcheck.py` |
| 7 | commit、push，並在另外兩台更新 | 第 05、06 章完整流程 |
| 8 | 改壞時退回上一個正常版本 | 第 05 章練習 5 |
| 9 | 看錯誤訊息判斷是哪一層出錯 | 第 07 章的分層判斷表 |
| 10 | 套件更新後壞掉，能退回已知可用的版本 | 第 10 章 |

**第 1～3、6、8 是最低門檻。** 只要有這五項，即使其他都不會，你也不會「失去這個工具」——
最壞情況就是停在某個可用的舊版本，工具照樣能用。

## 學習優先順序（五層）

**原則：每一層都用你自己的專案練習，學完一層就能多做一件事。不要跳層。**

### 第 1 層：現在立刻要懂的（約 3～5 小時）
> 目標：**就算什麼都不改，也不會失去這個工具。**

- [ ] 讀完第 02 章（三個版本），知道「其實是一份程式」
- [ ] 會開終端機，會用 `cd` 進入專案資料夾
- [ ] 會 `git status`、`git log --oneline`、`git pull`
- [ ] 會跑 `python tools/selfcheck.py`
- [ ] 會用 `疑難排解.bat` 看錯誤訊息
- [ ] 知道「最常見的壞掉 → 更新 yt-dlp」（第 07 章情境 A）
- [ ] 在 GitHub 上幫目前這個可用版本打一個 tag（第 05 章）

### 第 2 層：開始修改功能前要懂的（約 5～10 小時）
> 目標：**能安全地改一個小地方，改壞了能還原。**

- [ ] 第 03 章程式碼地圖：每個檔案、`ytscript.py` 每一區在做什麼
- [ ] 第 04 章資料流：從按下按鈕開始追一次
- [ ] Python 閱讀：`def`、`return`、字串、字典、`if`、縮排（第 04 章隨文教）
- [ ] Git：`switch -c` 開分支、`diff`、`add`、`commit`、`restore`
- [ ] 做一次第 06 章的「考試複習模式」範例（在分支上，做完可以丟掉）

### 第 3 層：開始自己除錯前要懂的（約 5～10 小時）
> 目標：**看到錯誤能判斷在哪一層，知道該修還是該退。**

- [ ] 第 07 章：錯誤分層判斷法、讀 Python 錯誤訊息（Traceback）
- [ ] `try / except` 的意思（這個專案到處都是，錯誤常被「吞掉」）
- [ ] 瀏覽器開發者工具的「Console」與「Network」分頁（看前端錯誤）
- [ ] 第 08 章：請 AI 除錯的提示詞
- [ ] pip：`pip show`、`pip install 套件==版本`

### 第 4 層：開始自己維護三個版本前要懂的（約 5～10 小時）
> 目標：**三台都能自己更新、自己退版。**

- [ ] 第 05 章完整：`push`、`merge`、衝突處理、`revert`、`tag`
- [ ] 手機：Termux 基本操作、`git pull` 後重新啟動
- [ ] 第 10 章：套件退版、模型重新下載、災難復原
- [ ] 看懂 `requirements/` 的版本清單；三台 selfcheck 的「套件是實測過的版本」都通過

### 第 5 層：未來有餘力再深入的
> 不影響維護能力，只是讓你更自在。

- 自己寫簡單的函式（不靠 AI）
- 理解 `threading`（為什麼伺服器能一邊聽寫一邊回應進度）
- 理解 HTTP（GET／POST、狀態碼 200／404／400）
- 第 11 章列出的結構改善（固定套件版本、加記錄檔等）

## 最後的客觀提醒

1. **這份手冊會過時。** 每次程式有大改，請 AI 幫你更新第 03 章的地圖（第 08 章有提示詞）。
2. **免費 GPT 的能力足夠處理這個專案 80% 的維護工作**（改提示詞、改畫面、加小功能、解釋錯誤）。
   剩下 20%（GPU／CUDA、Termux 編譯）連付費 AI 都常常要試好幾輪，對這些問題請優先「退版本」。
3. **最危險的不是你不會寫程式，而是改之前沒有存檔點。** 只要養成「改之前先 commit／開分支」的習慣，
   你就永遠不會失去這個工具。
